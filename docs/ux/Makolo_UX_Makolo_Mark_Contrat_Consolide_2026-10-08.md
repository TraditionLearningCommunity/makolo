# Makolo — **Makolo Mark**
## Contrat UX consolidé — intention, apport, compréhension, clarification, orchestration et handoff

**Date :** 2026-10-08  
**Statut :** contrat UX consolidé de référence — Makolo Mark  
**Actor Context :** `Profile` ou `Space` explicitement actif  
**Viewer :** Profile humain authentifié  
**Portée :** Web, Flutter, tablette/desktop adaptatif, Presentation, local-first, orchestration owner-backed  
**Base runtime vérifiée :** `main@788a744102e124feddbe0e17b30b8ede40fb2ebe`  
**Nature :** contrat UX, Presentation et orchestration ; ne crée aucun domaine métier `Mark`  
**Promesse produit :** **Makolo marche pour vous.**  
**Principe d’expérience :** **Pas le plaisir de rester. Le plaisir d’avancer.**

---

# 0. Décision structurante

Il existe un seul :

```text
Makolo Mark
```

Il n’existe pas :

```text
Personal Mark
Space Mark
Business Mark
Admin Mark
Creator Mark
Consumer Mark
```

comme expériences distinctes.

Le contexte courant donne son sens au Mark.

Invariant :

```text
MÊME MARK
+
MÊME GRAMMAIRE
+
MÊME IDENTITÉ VISUELLE
+
ACTOR CONTEXT DIFFÉRENT
+
OWNERS / AUTORITÉ / CONSÉQUENCES DIFFÉRENTS
```

---

# 1. Question humaine

Le Mark répond à :

> **J’ai quelque chose à donner à Makolo.**

La formulation d’ouverture visible peut rester :

> **Qu’est-ce que vous avez en tête ?**

L’entrée peut être :

- une intention ;
- une question ;
- du texte ;
- une voix ;
- une photo ;
- un document ;
- un lien ;
- une situation ;
- une demande de création ;
- une demande de préparation ;
- une demande de retrouver ;
- une demande de continuer.

---

# 2. Le Mark est une action centrale

Navigation personnelle :

```text
Maintenant | Découvrir | [Makolo Mark] | En cours | Moi
```

Navigation Space :

```text
Maintenant | Découvrir | [Makolo Mark] | Métier | Nous
```

Le Mark est :

```text
une action centrale
```

et non :

```text
une cinquième destination ordinaire
```

Il ne doit donc pas être conçu comme un onglet de contenu que l’on visite pour « voir ce qu’il y a ».

---

# 3. Personnalité UX

La personnalité Presentation du Mark est :

```text
intention + orchestration
```

Sa séquence cognitive est :

```text
EXPRIMER
→ COMPRENDRE
→ CLARIFIER si nécessaire
→ CONSÉQUENCE
→ CONFIRMER si nécessaire
→ HANDOFF / ACTION
```

Le Mark doit donner l’impression :

```text
je donne quelque chose
→ Makolo comprend suffisamment
→ Makolo me fait avancer
```

et non :

```text
je dois apprendre la taxonomie de Makolo
→ choisir un module
→ remplir un formulaire générique
→ comprendre le backend
```

---

# 4. Personnel et Space : même apparence

Décision gelée :

> **Le Mark ne change pas d’apparence fondamentale entre Personnel et Space.**

Les éléments suivants restent identiques :

- Makolo Mark officiel ;
- géométrie du champ principal ;
- hiérarchie perceptive ;
- rythme ;
- transitions ;
- mécanisme pièce jointe ;
- mécanisme voix ;
- mécanisme photo ;
- mécanisme lien ;
- états de clarification ;
- confirmation ;
- feedback ;
- adaptive ;
- accessibilité.

Le Space n’obtient pas :

- une version « professionnelle » plus dense ;
- un thème différent ;
- une console ;
- une palette d’outils ;
- un Mark noir ou administratif ;
- un vocabulaire backend.

---

# 5. Ce qui change réellement entre Personnel et Space

Ce qui change est :

```text
ACTOR_CONTEXT
AUTHORITY
CURRENT_CONTEXT
OWNER CANDIDATES
AVAILABLE CAPABILITIES
LEGAL CONSEQUENCES
HANDOFF DESTINATION
```

Exemple personnel :

```text
Actor = Moi

« Retrouve mon billet pour ce soir. »
→ Access personnel
```

Exemple Space :

```text
Actor = Mulykap

« Ouvre le Jour J de ce départ. »
→ Occurrence du Space
→ Operations owner
```

Même Mark.

Conséquence différente.

---

# 6. Personnel plus consommation, Space plus production : règle de tendance

Le produit peut exploiter une **tendance d’usage** :

```text
PERSONNEL
→ souvent chercher
→ obtenir
→ retrouver
→ préparer
→ rejoindre
→ poursuivre
→ utiliser ce qui existe déjà

SPACE
→ souvent créer
→ organiser
→ produire
→ préparer
→ opérer
→ délivrer
→ gérer une réalité collective
```

Mais cette tendance n’est pas une frontière métier absolue.

Un Profile peut opérer une Activity personnelle.

Un Space peut rechercher, obtenir, acheter ou consommer une capacité externe.

Donc :

```text
Profile
≠ consommateur universel

Space
≠ producteur universel
```

La différence influence les **conséquences probables et suggestions contextuelles**, jamais la nature visuelle du Mark.

---

# 7. Même Mark ≠ même résultat

L’input :

```text
« Trouve une formation en comptabilité »
```

dans le contexte personnel peut chercher une possibilité pour la personne.

Dans le contexte d’un Space, une formulation similaire peut chercher une formation pour l’équipe ou une possibilité utile au collectif.

Le Mark doit préserver :

```text
qui agit ?
pour qui ?
dans quel contexte ?
avec quelle autorité ?
```

---

# 8. Actor Context toujours explicite

Le Mark doit toujours pouvoir savoir si l’action est :

```text
Moi
```

ou :

```text
Mulykap
Fondation Upendo
Studio K
...
```

Dans un Space, le contexte peut être rappelé discrètement :

```text
Mulykap
Toutes mes responsabilités
```

ou un équivalent compact.

Ce rappel ne doit pas concurrencer l’input P3.

---

# 9. Changer d’acteur

Changer Actor Context est une action explicite.

Le Mark ne doit jamais décider silencieusement :

```text
« cette phrase semble professionnelle,
je vais agir pour Mulykap »
```

Interdit.

Si l’utilisateur a commencé dans `Moi`, l’intention reste personnelle jusqu’à changement explicite ou clarification nécessaire.

---

# 10. Responsibility lens dans un Space

Le contexte de responsabilité peut aider à réduire la lecture :

```text
Toutes mes responsabilités
Exploitation
Finance
Administration
Contrôle · Départ 14 h
...
```

Mais :

```text
responsibility lens
≠ authority
```

Le Mark doit revalider la Permission réelle avant toute mutation.

# 11. Le Mark ne possède aucune vérité métier

Invariant central :

```text
Mark
≠ domaine métier
```

Le Mark :

- comprend ;

- compose ;
- prépare ;
- clarifie ;

- orchestre ;

- Requirement ;
- Readiness ;

# 12. Pas de table universelle `MarkIntent`

Le besoin UX d’une entrée, d’un brouillon ou d’une clarification ne justifie pas automatiquement :

```text
MarkIntent
MarkConversation
MarkTask
MarkAction
MarkResult
```

comme nouveaux objets métier persistants.

Avant toute persistance, distinguer :

- draft local ;
- session d’intake ;
- read model ;
- journal technique limité ;
- objet owner réellement créé ;
- Conversation métier si un autre domaine la justifie.

---

# 13. Input principal

L’input est le dominant P3.

Golden :

```text
QUESTION / INPUT   P3
ATTACHMENTS        P1/P2
CONTINUE           P2
HEADER             P1
SUGGESTIONS        P0/P1
```

Le Mark ne doit pas commencer par une grille de capacités.

---

# 14. Formulation d’entrée

Référence :

> **Qu’est-ce que vous avez en tête ?**

Sous-texte possible :

> **Dites-le comme vous le diriez à quelqu’un.**

Le produit ne doit pas demander :

```text
Choisissez un workflow
Choisissez un type d’objet
Choisissez un agent
Sélectionnez une compétence
```

avant que le sens humain le nécessite.

---

# 15. Multi-intent

Une entrée peut contenir plusieurs intentions.

Exemple :

```text
« J’ai reçu cette attestation de l’université.
Ajoute-la à ma candidature et dis-moi s’il manque encore quelque chose. »
```

Le Mark ne doit pas imposer une classification prématurée.

Il doit comprendre la situation entière, puis séparer les conséquences si nécessaire.

---

# 16. Comprendre suffisamment

Principe :

> **Le Mark doit comprendre assez pour produire la prochaine conséquence correcte.**

Il ne doit pas chercher à produire une compréhension totale du monde avant d’agir.

Il doit identifier :

- ce qui semble être demandé ;
- le contexte ;
- la cible éventuelle ;
- les inconnues réellement bloquantes ;
- l’owner probable ;
- l’autorité nécessaire ;
- ce qui peut être préparé sans risque.

---

# 17. Comprendre ≠ croire

```text
COMPRENDRE
≠
ÉTABLIR COMME VRAI
```

Un texte peut dire :

```text
« Mon vol a été annulé. »
```

Le Mark peut comprendre la déclaration.

Il ne doit pas transformer automatiquement cette déclaration en fait canonique externe si le domaine exige une source ou une vérification.

---

# 18. Comprendre ≠ conserver

Une entrée peut servir uniquement à :

- identifier une intention ;
- répondre ;
- retrouver ;
- préparer ;
- handoff.

Elle n’a pas à devenir durable.

---

# 19. Comprendre ≠ agir

Le Mark peut comprendre parfaitement une demande et ne pas avoir :

- Permission ;
- données ;
- capability ;
- owner disponible ;
- confirmation humaine.

La bonne sortie peut être :

```text
compris
+
non exécuté
```

---

# 20. Les sept capacités sémantiques

Le Mark peut composer sept familles fonctionnelles.

## 20.1 Comprendre

Établir sens, contexte et incertitude utile.

## 20.2 Retrouver

Récupérer une réalité déjà connue, reliée ou explicitement désignée.

## 20.3 Réutiliser

Employer une réalité déjà connue dans un nouveau contexte lorsque compatible.

## 20.4 Conserver

Transformer l’entrée en ressource ou vérité durable via le bon owner.

## 20.5 Faire avancer

Continuer une réalité existante.

## 20.6 Faire exister

Créer une nouvelle réalité lorsqu’elle doit vraiment exister.

## 20.7 Continuer pour moi

Exprimer une délégation temporelle bornée vers Watch, Automation, rappel ou autre owner réel.

---

# 21. Retrouver ≠ Découvrir

Invariant :

```text
RETROUVER
→ réalité déjà reliée ou désignée

DÉCOUVRIR
→ champ de nouvelles possibilités
```

Exemples :

```text
« retrouve mon billet »
→ Mark / Retrouver

« trouve un billet pour Kinshasa »
→ Découvrir

« retrouve ma candidature »
→ Mark / Retrouver

« trouve une bourse »
→ Découvrir
```

---

# 22. Frontière Mark ↔ Découvrir

Règle gelée :

```text
champ de possibilités indéterminé
→ Découvrir

cible suffisamment déterminée
→ orchestration directe
```

Le Mark reçoit l’intention de découverte.

Découvrir possède l’expérience d’exploration.

---

# 23. URL fournie ≠ Discovery automatique

Une URL donnée explicitement au Mark est une source d’entrée.

Elle peut être :

- comprise ;
- retrouvée ;
- comparée ;
- évaluée ;
- transmise à une capacité de recherche/knowledge.

Elle ne devient pas automatiquement un item Discover ou une vérité canonique.

---

# 24. Web Research et Mark

Lorsque l’intention nécessite de chercher dans le monde externe, le Mark peut déclencher ou handoff vers une capacité de recherche Makolo.

Mais :

```text
Mark
≠ Web Search engine

Web Search result
≠ vérité canonique
```

Les responsabilités de provenance, interprétation, résolution et admission restent séparées.

---

# 25. Retrouver ≠ Réutiliser

Trouver un passeport dans Moi ne signifie pas qu’il satisfait le Requirement courant.

Flux :

```text
Retrouver
→ owner Resource

Réutiliser
→ vérifier compatibilité contextuelle

Readiness / Requirement
→ décide de la suffisance
```

---

# 26. Réutiliser ≠ copier

Réutiliser un document, Proof ou Credential ne doit pas créer une copie arbitraire de la vérité.

Il faut référencer ou handoff selon les contrats propriétaires.

---

# 27. Conserver

Recevoir une pièce ne signifie pas conserver durablement.

```text
recevoir
≠ conserver
```

Le type de fichier ne choisit pas sa destination.

```text
PDF
≠ PersonalAsset automatiquement
```

---

# 28. Support ≠ vérité

Invariant :

```text
photo
document
audio
URL
texte
≠ vérité métier automatique
```

Ils peuvent soutenir une vérité, une compréhension ou une preuve.

L’owner décide.

---

# 29. Conserver ≠ vérifier

Ajouter une attestation à Makolo ne signifie pas :

```text
attestation vérifiée
```

Trust reste owner.

---

# 30. Conserver ≠ publier

Une ressource reçue dans Mark n’est jamais rendue publique par défaut.

```text
intake privé
≠ publication
```

---

# 31. Faire avancer

Le Mark doit reprendre la réalité là où elle en est.

Exemple :

```text
« Continue ma candidature »
```

doit essayer de retrouver la Journey/Dossier réelle.

Il ne doit pas créer une seconde candidature.

---

# 32. Rien à faire

Une conséquence correcte peut être :

```text
Tout est déjà prêt.
Rien à faire pour le moment.
```

Le Mark n’invente pas une action pour satisfaire la demande d’interaction.

---

# 33. Faire exister

Créer une réalité exige :

- owner réel ;
- contexte ;
- responsabilité ;
- données minimales suffisantes ;
- Permission ;
- absence de contradiction ;
- handoff canonique.

---

# 34. Existence ≠ publication

Invariant :

```text
CREATE
≠ PUBLISH
≠ DISCOVERABLE
```

Une Activity peut être créée/configurée sans être publique.

---

# 35. Incomplet ≠ faux

Le Mark peut préparer une nouvelle réalité incomplète si l’owner permet un draft réel.

Il ne doit pas inventer les champs manquants.

---

# 36. No Orphan Content

Toute réalité ou ressource créée via Mark doit avoir :

```text
contexte
+
finalité
+
owner
```

Pas de document, média ou objet générique sans destination démontrée.

---

# 37. Continuer pour moi

Exemples :

```text
« Continue à chercher des bourses comme celle-ci. »
« Préviens-moi si une place se libère. »
« Rappelle-moi de vérifier ça demain. »
```

Le Mark doit handoff vers une capacité réelle.

---

# 38. Surveiller ≠ agir

Une Watch peut observer.

Elle n’accorde pas automatiquement le droit d’agir quand la condition devient vraie.

---

# 39. Délégation bornée

Une délégation doit avoir :

- objet ;
- finalité ;
- condition ou cadence ;
- possibilité d’arrêt ;
- owner.

Le Mark ne doit pas créer un « agent permanent » vague.

---

# 40. Silence par défaut

Un changement backend n’est pas une raison suffisante pour interrompre.

Le Mark et les capacités qu’il déclenche respectent :

```text
changement
→ évaluer conséquence
→ notification seulement si utile
```

---

# 41. Modalités d’entrée

Le Mark doit pouvoir accueillir progressivement :

```text
texte
voix
photo
document
lien
contexte sélectionné
situation
```

La disponibilité effective dépend du client et du runtime.

---

# 42. Texte

Le texte est l’entrée la plus universelle.

Il ne doit pas être limité conceptuellement à une « commande ».

Il peut contenir :

- intention ;
- description ;
- question ;
- contexte ;
- correction ;
- conséquence désirée.

---

# 43. Voix

La voix est une modalité d’entrée.

Elle ne crée pas un produit Voice séparé.

UX candidate :

```text
maintenir / toucher
→ enregistrer
→ transcription / compréhension
→ vérifier si ambigu
→ continuer
```

---

# 44. Audio brut

Le fichier audio brut n’a pas besoin d’être conservé durablement si seule la transcription est utile.

Privacy-first :

```text
capture
≠ conservation permanente
```

---

# 45. Photo

Une photo peut servir à :

- identifier ;
- illustrer ;
- comprendre ;
- préparer un document ;
- fournir un support owner.

Elle ne devient pas automatiquement Proof.

---

# 46. Document

Un document peut être :

- support d’entrée ;
- Personal Asset candidat ;
- JourneyArtifact candidat ;
- pièce attendue ;
- Proof candidate ;
- Resource.

Le type réel dépend du contexte et de l’owner.

---

# 47. Lien

Un lien est une référence.

Il ne doit pas être admis automatiquement comme vérité.

Il peut nécessiter :

- récupération ;
- provenance ;
- fraîcheur ;
- interprétation ;
