# Makolo — **Makolo Mark**
## Contrat UX consolidé — intention, apport, compréhension, clarification, orchestration et handoff

**Date :** 2026-10-08  
**Statut :** contrat UX consolidé de référence — Makolo Mark  
**Actor Context :** `Profile` ou `Space` explicitement actif  
**Viewer :** Profile humain authentifié  
**Portée :** Web, Flutter, tablette/desktop adaptatif, Presentation, local-first, orchestration owner-backed  
**Base runtime vérifiée :** `main@788a744102e124feddbe0e17b30b8ede40fb2ebe`  
**Nature :** contrat UX, Presentation et orchestration ; ne crée aucun domaine métier `Mark`  
**Promesse produit :** **Makolo marche pour vous.**  
**Principe d’expérience :** **Pas le plaisir de rester. Le plaisir d’avancer.**

---

# 0. Décision structurante

Il existe un seul :

```text
Makolo Mark
```

Il n’existe pas :

```text
Personal Mark
Space Mark
Business Mark
Admin Mark
Creator Mark
Consumer Mark
```

comme expériences distinctes.

Le contexte courant donne son sens au Mark.

Invariant :

```text
MÊME MARK
+
MÊME GRAMMAIRE
+
MÊME IDENTITÉ VISUELLE
+
ACTOR CONTEXT DIFFÉRENT
+
OWNERS / AUTORITÉ / CONSÉQUENCES DIFFÉRENTS
```

---

# 1. Question humaine

Le Mark répond à :

> **J’ai quelque chose à donner à Makolo.**

La formulation d’ouverture visible peut rester :

> **Qu’est-ce que vous avez en tête ?**

L’entrée peut être :

- une intention ;
- une question ;
- du texte ;
- une voix ;
- une photo ;
- un document ;
- un lien ;
- une situation ;
- une demande de création ;
- une demande de préparation ;
- une demande de retrouver ;
- une demande de continuer.

---

# 2. Le Mark est une action centrale

Navigation personnelle :

```text
Maintenant | Découvrir | [Makolo Mark] | En cours | Moi
```

Navigation Space :

```text
Maintenant | Découvrir | [Makolo Mark] | Métier | Nous
```

Le Mark est :

```text
une action centrale
```

et non :

```text
une cinquième destination ordinaire
```

Il ne doit donc pas être conçu comme un onglet de contenu que l’on visite pour « voir ce qu’il y a ».

---

# 3. Personnalité UX

La personnalité Presentation du Mark est :

```text
intention + orchestration
```

Sa séquence cognitive est :

```text
EXPRIMER
→ COMPRENDRE
→ CLARIFIER si nécessaire
→ CONSÉQUENCE
→ CONFIRMER si nécessaire
→ HANDOFF / ACTION
```

Le Mark doit donner l’impression :

```text
je donne quelque chose
→ Makolo comprend suffisamment
→ Makolo me fait avancer
```

et non :

```text
je dois apprendre la taxonomie de Makolo
→ choisir un module
→ remplir un formulaire générique
→ comprendre le backend
```

---

# 4. Personnel et Space : même apparence

Décision gelée :

> **Le Mark ne change pas d’apparence fondamentale entre Personnel et Space.**

Les éléments suivants restent identiques :

- Makolo Mark officiel ;
- géométrie du champ principal ;
- hiérarchie perceptive ;
- rythme ;
- transitions ;
- mécanisme pièce jointe ;
- mécanisme voix ;
- mécanisme photo ;
- mécanisme lien ;
- états de clarification ;
- confirmation ;
- feedback ;
- adaptive ;
- accessibilité.

Le Space n’obtient pas :

- une version « professionnelle » plus dense ;
- un thème différent ;
- une console ;
- une palette d’outils ;
- un Mark noir ou administratif ;
- un vocabulaire backend.

---

# 5. Ce qui change réellement entre Personnel et Space

Ce qui change est :

```text
ACTOR_CONTEXT
AUTHORITY
CURRENT_CONTEXT
OWNER CANDIDATES
AVAILABLE CAPABILITIES
LEGAL CONSEQUENCES
HANDOFF DESTINATION
```

Exemple personnel :

```text
Actor = Moi

« Retrouve mon billet pour ce soir. »
→ Access personnel
```

Exemple Space :

```text
Actor = Mulykap

« Ouvre le Jour J de ce départ. »
→ Occurrence du Space
→ Operations owner
```

Même Mark.

Conséquence différente.

---

# 6. Personnel plus consommation, Space plus production : règle de tendance

Le produit peut exploiter une **tendance d’usage** :

```text
PERSONNEL
→ souvent chercher
→ obtenir
→ retrouver
→ préparer
→ rejoindre
→ poursuivre
→ utiliser ce qui existe déjà

SPACE
→ souvent créer
→ organiser
→ produire
→ préparer
→ opérer
→ délivrer
→ gérer une réalité collective
```

Mais cette tendance n’est pas une frontière métier absolue.

Un Profile peut opérer une Activity personnelle.

Un Space peut rechercher, obtenir, acheter ou consommer une capacité externe.

Donc :

```text
Profile
≠ consommateur universel

Space
≠ producteur universel
```

La différence influence les **conséquences probables et suggestions contextuelles**, jamais la nature visuelle du Mark.

---

# 7. Même Mark ≠ même résultat

L’input :

```text
« Trouve une formation en comptabilité »
```

dans le contexte personnel peut chercher une possibilité pour la personne.

Dans le contexte d’un Space, une formulation similaire peut chercher une formation pour l’équipe ou une possibilité utile au collectif.

Le Mark doit préserver :

```text
qui agit ?
pour qui ?
dans quel contexte ?
avec quelle autorité ?
```

---

# 8. Actor Context toujours explicite

Le Mark doit toujours pouvoir savoir si l’action est :

```text
Moi
```

ou :

```text
Mulykap
Fondation Upendo
Studio K
...
```

Dans un Space, le contexte peut être rappelé discrètement :

```text
Mulykap
Toutes mes responsabilités
```

ou un équivalent compact.

Ce rappel ne doit pas concurrencer l’input P3.

---

# 9. Changer d’acteur

Changer Actor Context est une action explicite.

Le Mark ne doit jamais décider silencieusement :

```text
« cette phrase semble professionnelle,
je vais agir pour Mulykap »
```

Interdit.

Si l’utilisateur a commencé dans `Moi`, l’intention reste personnelle jusqu’à changement explicite ou clarification nécessaire.

---

# 10. Responsibility lens dans un Space

Le contexte de responsabilité peut aider à réduire la lecture :

```text
Toutes mes responsabilités
Exploitation
Finance
Administration
Contrôle · Départ 14 h
...
```

Mais :

```text
responsibility lens
≠ authority
```

Le Mark doit revalider la Permission réelle avant toute mutation.

# 12. Pas de table universelle `MarkIntent`

Le besoin UX d’une entrée, d’un brouillon ou d’une clarification ne justifie pas automatiquement :

```text
MarkIntent
MarkConversation
MarkTask
MarkAction
MarkResult
```

comme nouveaux objets métier persistants.

Avant toute persistance, distinguer :

- draft local ;
- session d’intake ;
- read model ;
- journal technique limité ;
- objet owner réellement créé ;
- Conversation métier si un autre domaine la justifie.

# 13. Input principal

L’input est le dominant P3.

Golden :

```text
QUESTION / INPUT   P3
ATTACHMENTS        P1/P2
CONTINUE           P2
HEADER             P1
SUGGESTIONS        P0/P1
```

Le Mark ne doit pas commencer par une grille de capacités.

---

# 14. Formulation d’entrée

Référence :

> **Qu’est-ce que vous avez en tête ?**

Sous-texte possible :

> **Dites-le comme vous le diriez à quelqu’un.**

Le produit ne doit pas demander :

```text
Choisissez un workflow
Choisissez un type d’objet
Choisissez un agent
Sélectionnez une compétence
```

avant que le sens humain le nécessite.

---

# 15. Multi-intent

Une entrée peut contenir plusieurs intentions.

Exemple :

```text
« J’ai reçu cette attestation de l’université.
Ajoute-la à ma candidature et dis-moi s’il manque encore quelque chose. »
```

Le Mark ne doit pas imposer une classification prématurée.

Il doit comprendre la situation entière, puis séparer les conséquences si nécessaire.

---

# 16. Comprendre suffisamment

Principe :

> **Le Mark doit comprendre assez pour produire la prochaine conséquence correcte.**

Il ne doit pas chercher à produire une compréhension totale du monde avant d’agir.

Il doit identifier :

- ce qui semble être demandé ;
- le contexte ;
- la cible éventuelle ;
- les inconnues réellement bloquantes ;
- l’owner probable ;
- l’autorité nécessaire ;
- ce qui peut être préparé sans risque.

---

# 17. Comprendre ≠ croire

```text
COMPRENDRE
≠
ÉTABLIR COMME VRAI
```

Un texte peut dire :

```text
« Mon vol a été annulé. »
```

Le Mark peut comprendre la déclaration.

Il ne doit pas transformer automatiquement cette déclaration en fait canonique externe si le domaine exige une source ou une vérification.

---

# 18. Comprendre ≠ conserver

Une entrée peut servir uniquement à :

- identifier une intention ;
- répondre ;
- retrouver ;
- préparer ;
- handoff.

Elle n’a pas à devenir durable.

---

# 19. Comprendre ≠ agir

Le Mark peut comprendre parfaitement une demande et ne pas avoir :

- Permission ;
- données ;
- capability ;
- owner disponible ;
- confirmation humaine.

La bonne sortie peut être :

```text
compris
+
non exécuté
```

---

# 20. Les sept capacités sémantiques

Le Mark peut composer sept familles fonctionnelles.

## 20.1 Comprendre

Établir sens, contexte et incertitude utile.

## 20.2 Retrouver

Récupérer une réalité déjà connue, reliée ou explicitement désignée.

## 20.3 Réutiliser

Employer une réalité déjà connue dans un nouveau contexte lorsque compatible.

## 20.4 Conserver

Transformer l’entrée en ressource ou vérité durable via le bon owner.

## 20.5 Faire avancer

Continuer une réalité existante.

## 20.6 Faire exister

Créer une nouvelle réalité lorsqu’elle doit vraiment exister.

## 20.7 Continuer pour moi

Exprimer une délégation temporelle bornée vers Watch, Automation, rappel ou autre owner réel.

---

# 21. Retrouver ≠ Découvrir

Invariant :

```text
RETROUVER
→ réalité déjà reliée ou désignée

DÉCOUVRIR
→ champ de nouvelles possibilités
```

Exemples :

```text
« retrouve mon billet »
→ Mark / Retrouver

« trouve un billet pour Kinshasa »
→ Découvrir

« retrouve ma candidature »
→ Mark / Retrouver

« trouve une bourse »
→ Découvrir
```

---

# 22. Frontière Mark ↔ Découvrir

Règle gelée :

```text
champ de possibilités indéterminé
→ Découvrir

cible suffisamment déterminée
→ orchestration directe
```

Le Mark reçoit l’intention de découverte.

Découvrir possède l’expérience d’exploration.

---

# 23. URL fournie ≠ Discovery automatique

Une URL donnée explicitement au Mark est une source d’entrée.

Elle peut être :

- comprise ;
- retrouvée ;
- comparée ;
- évaluée ;
- transmise à une capacité de recherche/knowledge.

Elle ne devient pas automatiquement un item Discover ou une vérité canonique.

---

# 24. Web Research et Mark

Lorsque l’intention nécessite de chercher dans le monde externe, le Mark peut déclencher ou handoff vers une capacité de recherche Makolo.

Mais :

```text
Mark
≠ Web Search engine

Web Search result
≠ vérité canonique
```

Les responsabilités de provenance, interprétation, résolution et admission restent séparées.

---

# 25. Retrouver ≠ Réutiliser

Trouver un passeport dans Moi ne signifie pas qu’il satisfait le Requirement courant.

Flux :

```text
Retrouver
→ owner Resource

Réutiliser
→ vérifier compatibilité contextuelle

Readiness / Requirement
→ décide de la suffisance
```

---

# 26. Réutiliser ≠ copier

Réutiliser un document, Proof ou Credential ne doit pas créer une copie arbitraire de la vérité.

Il faut référencer ou handoff selon les contrats propriétaires.

---

# 27. Conserver

Recevoir une pièce ne signifie pas conserver durablement.

```text
recevoir
≠ conserver
```

Le type de fichier ne choisit pas sa destination.

```text
PDF
≠ PersonalAsset automatiquement
```

---

# 28. Support ≠ vérité

Invariant :

```text
photo
document
audio
URL
texte
≠ vérité métier automatique
```

Ils peuvent soutenir une vérité, une compréhension ou une preuve.

L’owner décide.

---

# 29. Conserver ≠ vérifier

Ajouter une attestation à Makolo ne signifie pas :

```text
attestation vérifiée
```

Trust reste owner.

---

# 30. Conserver ≠ publier

Une ressource reçue dans Mark n’est jamais rendue publique par défaut.

```text
intake privé
≠ publication
```

---

# 31. Faire avancer

Le Mark doit reprendre la réalité là où elle en est.

Exemple :

```text
« Continue ma candidature »
```

doit essayer de retrouver la Journey/Dossier réelle.

Il ne doit pas créer une seconde candidature.

---

# 32. Rien à faire

Une conséquence correcte peut être :

```text
Tout est déjà prêt.
Rien à faire pour le moment.
```

Le Mark n’invente pas une action pour satisfaire la demande d’interaction.

---

# 33. Faire exister

Créer une réalité exige :

- owner réel ;
- contexte ;
- responsabilité ;
- données minimales suffisantes ;
- Permission ;
- absence de contradiction ;
- handoff canonique.

---

# 34. Existence ≠ publication

Invariant :

```text
CREATE
≠ PUBLISH
≠ DISCOVERABLE
```

Une Activity peut être créée/configurée sans être publique.

---

# 35. Incomplet ≠ faux

Le Mark peut préparer une nouvelle réalité incomplète si l’owner permet un draft réel.

Il ne doit pas inventer les champs manquants.

---

# 36. No Orphan Content

Toute réalité ou ressource créée via Mark doit avoir :

```text
contexte
+
finalité
+
owner
```

Pas de document, média ou objet générique sans destination démontrée.

---

# 37. Continuer pour moi

Exemples :

```text
« Continue à chercher des bourses comme celle-ci. »
« Préviens-moi si une place se libère. »
« Rappelle-moi de vérifier ça demain. »
```

Le Mark doit handoff vers une capacité réelle.

---

# 38. Surveiller ≠ agir

Une Watch peut observer.

Elle n’accorde pas automatiquement le droit d’agir quand la condition devient vraie.

---

# 39. Délégation bornée

Une délégation doit avoir :

- objet ;
- finalité ;
- condition ou cadence ;
- possibilité d’arrêt ;
- owner.

Le Mark ne doit pas créer un « agent permanent » vague.

---

# 40. Silence par défaut

Un changement backend n’est pas une raison suffisante pour interrompre.

Le Mark et les capacités qu’il déclenche respectent :

```text
changement
→ évaluer conséquence
→ notification seulement si utile
```

---

# 41. Modalités d’entrée

Le Mark doit pouvoir accueillir progressivement :

```text
texte
voix
photo
document
lien
contexte sélectionné
situation
```

La disponibilité effective dépend du client et du runtime.

---

# 42. Texte

Le texte est l’entrée la plus universelle.

Il ne doit pas être limité conceptuellement à une « commande ».

Il peut contenir :

- intention ;
- description ;
- question ;
- contexte ;
- correction ;
- conséquence désirée.

---

# 43. Voix

La voix est une modalité d’entrée.

Elle ne crée pas un produit Voice séparé.

UX candidate :

```text
maintenir / toucher
→ enregistrer
→ transcription / compréhension
→ vérifier si ambigu
→ continuer
```

---

# 44. Audio brut

Le fichier audio brut n’a pas besoin d’être conservé durablement si seule la transcription est utile.

Privacy-first :

```text
capture
≠ conservation permanente
```

---

# 45. Photo

Une photo peut servir à :

- identifier ;
- illustrer ;
- comprendre ;
- préparer un document ;
- fournir un support owner.

Elle ne devient pas automatiquement Proof.

---

# 46. Document

Un document peut être :

- support d’entrée ;
- Personal Asset candidat ;
- JourneyArtifact candidat ;
- pièce attendue ;
- Proof candidate ;
- Resource.

Le type réel dépend du contexte et de l’owner.

---

# 47. Lien

Un lien est une référence.

Il ne doit pas être admis automatiquement comme vérité.

Il peut nécessiter :

- récupération ;
- provenance ;
- fraîcheur ;
- interprétation ;
- vérification.

---

# 48. Pièces jointes — hiérarchie

Golden :

```text
ATTACHMENTS = P1/P2
```

Elles soutiennent l’intention.

Elles ne dominent pas l’input sauf si l’objet lui-même est le sujet principal de la demande.

---

# 49. Plusieurs pièces jointes

Le Mark peut accepter plusieurs supports si nécessaire.

Mais l’UX ne doit pas devenir un gestionnaire de fichiers.

Chaque pièce doit rester associée à l’intake courant.

---

# 50. Contexte d’entrée depuis une autre surface

Le Mark peut être ouvert depuis :

- Now ;
- Discover ;
- En cours ;
- Moi ;
- Métier ;
- Nous ;
- Jour J ;
- une profondeur owner.

Le contexte sélectionné peut être transmis explicitement.

---

# 51. Selected context

Exemple :

```text
Discover
→ Activity X sélectionnée
→ Mark

```

Le Mark reçoit :

```text
selected reality
+
Actor Context
+
intention
```

sans recopier la vérité.

# 52. Context preservation

Si le Mark est annulé ou terminé sans handoff, le retour doit préserver :

- surface d’origine ;
- sélection ;
- scroll ;
- query ;
- filtres ;
- Actor Context.

# 54. Header


# 55. Pas de titre lourd `Makolo Mark`

Le symbole et la question suffisent souvent.

Le grand titre :

```text
Makolo Mark
```

n’est pas obligatoire au-dessus de l’input.

Il peut être utile en Web actuel ou accessibilité, mais ne doit pas rivaliser avec la question.

- `+` ;

# 57. Géométrie du Mark

- conteneur ;

# 58. Activation du Mark

```text
press feedback
```

# 59. Même Mark central dans les deux shells

Le bouton central conserve :

- même asset ;
- même taille structurelle candidate ;
- même semantics ;
- même feedback ;
- même position cognitive.

---

# 60. Suggestions

Les suggestions sont :

```text
P0/P1
```

Elles sont facultatives.

Elles ne doivent pas devenir une palette d’outils.

---

# 61. Suggestions personnelles

Exemples possibles si contextuellement utiles :

```text
Retrouver quelque chose
Explorer une possibilité
Continuer une démarche
```

Ces suggestions ne sont pas un menu fixe.

---

# 62. Suggestions Space

Exemples possibles si contextuellement utiles :

```text
Retrouver une réalité
Préparer quelque chose
Continuer une opération
```

ou des formulations métier.

Mais elles ne doivent jamais exposer toute la taxonomie.

---

# 63. Suggestions et tendance production/consommation

Le contexte peut influer sur les suggestions :

```text
Moi
→ davantage de verbes orientés trouver / obtenir / reprendre

Space
→ davantage de verbes orientés créer / préparer / opérer
```

uniquement si l’historique et les capabilities le justifient.

L’UI de base reste identique.

---

# 64. Clarification

Le Mark ne doit demander que ce qui bloque réellement la prochaine conséquence utile.

Pas de questionnaire préventif.

---

# 65. Une clarification à la fois

Préférence UX :

```text
question la plus structurante
→ réponse
→ re-évaluation
```

plutôt que :

```text
formulaire de 12 questions
```

sauf si l’owner exige réellement un formulaire structuré.

---

# 66. Clarification par options

Lorsque plusieurs réalités correspondent :

```text
Plusieurs démarches peuvent correspondre.
Laquelle voulez-vous continuer ?
```

Le Mark peut présenter quelques options bornées.

Pas de liste infinie.

---

# 67. Unknown ≠ not found globally

Ne pas trouver dans les réalités accessibles signifie :

```text
non retrouvé dans ce contexte
```

et non :

```text
cela n’existe pas
```

---

# 68. Unsupported

Si un owner handoff n’est pas disponible :

```text
Makolo ne peut pas encore faire cela ici.
```

Le Mark ne doit pas simuler la capacité.

---

# 69. Forbidden

Quand l’intention est comprise mais l’autorité absente :

```text
Makolo comprend l’action
+
ne l’exécute pas
+
explique la limite
+
propose la voie légitime si elle existe
```

---

# 70. L’autorité ne vient jamais du langage

Une phrase impérative :

```text
« Ajoute Marie à l’équipe »
```

ne crée aucune Permission.

Le Mark doit interroger les owners autoritatifs.

---

# 71. Confirmation

Une confirmation est requise lorsque l’action franchit une conséquence humaine significative.

Exemples :

- ajouter un membre ;
- attribuer une autorité ;
- publier ;
- payer ;
- réserver ;
- soumettre ;
- annuler ;
- partager une donnée privée ;
- supprimer ;
- engager une dépense ;
- agir au nom d’un Space.

Selon le domaine, certaines actions peuvent être sûres sans confirmation supplémentaire.

---

# 72. Confirmation parle de conséquence

Bon :

```text
Ajouter Marie à l’équipe de Mulykap
avec le rôle Responsable exploitation.
```

Mauvais :

```text
Exécuter action ADD_TEAM_MEMBER ?
```

---

# 73. Pas de double confirmation inutile

Si l’utilisateur vient déjà d’effectuer une action explicite dans une surface owner et que le owner n’exige pas une seconde confirmation, Mark ne doit pas rajouter une friction rituelle.

---

# 74. Décision humaine réelle

Makolo peut :

- préparer ;
- vérifier ;
- retrouver ;
- comparer ;
- expliquer ;
- remplir ;
- simuler.

Il ne tranche pas silencieusement un arbitrage de valeur non délégué.

---

# 75. Handoff

Une fois la conséquence déterminée, le Mark handoff vers :

Personnel :

- Maintenant ;
- Découvrir ;
- En cours ;
- Moi ;
- Jour J ;
- domaine propriétaire ;
- surface secondaire.

Space :

- Maintenant ;
- Découvrir ;
- Métier ;
- Nous ;
- Personnes & relations ;
- Piloter ;
- Jour J ;
- Scanner ;
- domaine propriétaire.

---

# 76. Handoff ≠ navigation arbitraire

Le handoff doit représenter la destination naturelle de la réalité.

Le Mark ne devient pas un router de pages basé sur mots-clés visibles.

---

# 77. Handoff après création

Exemple Space :

```text
« Crée un nouveau programme de comptabilité. »
→ owner Activity / education
→ création confirmée
→ ouvrir Programme créé
```

Le Mark ne garde pas une copie comme `MarkResult`.

---

# 78. Handoff après retrouver

Exemple personnel :

```text
« Retrouve mon billet. »
→ Access
→ Access detail / Jour J si pertinent
```

---

# 79. Handoff vers Now

Seulement si la conséquence mérite l’attention présente.

Le Mark ne place pas toute action terminée dans Now.

---

# 80. Handoff vers Moi

Lorsqu’une vérité durable est désormais disponible.

Exemple :

```text
Credential délivré
→ Moi peut le présenter
```

---

# 81. Handoff vers En cours

Lorsqu’une poursuite personnelle réelle est engagée et continue.

Le Mark ne crée pas `En cours`.

---

# 82. Handoff vers Métier

Dans un Space, une nouvelle réalité opérée ou une réalité durable existante peut ouvrir le Métier contextualisé.

---

# 83. Jour J

Le Mark peut ouvrir Jour J si l’Occurrence est admissible.

Il ne fabrique pas une Occurrence actuelle.

---

# 84. Live

Le Mark peut handoff vers Live seulement via les contrats Jour J/Operations existants.

Une demande :

```text
« Montre-moi ce qui se passe maintenant »
```

n’autorise pas à inventer un état Live.

---

# 85. Scanner

Dans un Space, ouvrir Scanner exige :

- Occurrence déterminée ;
- capability ;
- authority ;
- contexte owner.

Le Mark ne valide pas lui-même l’Access.

---

# 86. Mark ≠ chatbot

Le Mark n’est pas conçu comme :

- messagerie infinie ;
- historique de chats ;
- assistant social ;
- fenêtre de conversation persistante ;
- produit de rétention conversationnelle.

---

# 87. Clarification conversationnelle bornée

Une interaction peut prendre la forme :

```text
input
→ question
→ réponse
→ conséquence
```

Cela ne crée pas automatiquement un `Chat`.

---

# 88. Historique

Pas de sidebar permanente :

```text
History
Chats
Drafts
Sources
Tools
Agents
Templates
```

L’historique éventuel appartient aux propriétaires ou à une capacité dédiée.

---

# 89. Mark ≠ palette d’agents

Interdit :

```text
Choisir :
- Agent Recherche
- Agent Documents
- Agent Finance
- Agent Transport
- Agent Team
```

L’orchestration interne doit rester invisible quand elle n’aide pas la décision humaine.

---

# 90. Mark ≠ panneau « Ce que Makolo peut faire »

La largeur desktop ne doit pas devenir une page marketing de capabilities.

Le Mark commence par l’intention.

---

# 91. Intelligence provider-neutral

Le Mark peut utiliser des capacités d’intelligence.

Mais l’expérience ne dépend pas d’un fournisseur ou modèle nommé.

```text
Makolo
→ capability
→ provider éventuel
```

Le fournisseur ne devient pas propriétaire de l’intention ou de la vérité.

---

# 92. Knowledge vs action

Le Mark peut demander une capacité de connaissance.

Mais :

```text
connaissance candidate
≠ action autorisée
```

Les domaines Makolo transforment ensuite ce qui est établi en préparation/action.

---

# 93. Brouillon

Un brouillon doit exister lorsque perdre l’entrée serait significatif.

Exemples :

- texte long ;
- plusieurs pièces jointes ;
- création structurée ;
- contexte de candidature ;
- préparation Space complexe.

---

# 94. Autosave

Autosave possible si :

- compréhensible ;
- sûr ;
- conflits gérés ;
- état clair.

États candidats :

```text
Enregistré sur cet appareil
Enregistrement…
Échec d’enregistrement
```

---

# 95. Brouillon local ≠ soumis

Invariant :

```text
brouillon local
≠ soumis
≠ exécuté
≠ confirmé
```

---

# 96. Offline

Le Mark peut rester utile hors ligne pour :

- saisir ;
- joindre un fichier local ;
- prendre une photo ;
- enregistrer une note ;
- préparer une demande ;
- conserver un draft.

Mais il ne doit pas inventer les résultats distants.

---

# 97. Classes d’opération

Le Mark peut orchestrer des opérations A/B/C/D.

En pratique, l’intake lui-même peut être local.

De nombreuses conséquences sont :

```text
C — préparables localement, confirmées à distance
ou
D — intrinsèquement distantes
```

---

# 98. Pas de blind retry

Pour une mutation owner dont l’idempotence n’est pas démontrée :

```text
pas de retry aveugle
```

Le Mark doit éviter une double réservation, double soumission ou double création.

---

# 99. Outbox

L’Outbox appartient au kernel sync.

Le Mark peut produire une intention/pending owner-backed lorsqu’un contrat le permet.

Il ne crée pas une vérité Mark parallèle.

---

# 100. Crash recovery

Après crash :

- détecter draft ;
- restaurer si sûr ;
- proposer `Reprendre` si nécessaire ;
- revalider contexte et owner.

---

# 101. Contexte devenu invalide

Exemple :

```text
draft Mark
→ sélectionnait Occurrence X
→ l’Occurrence est désormais annulée
```

Le draft peut rester.

La cible doit être revalidée.

---

# 102. Changement d’Actor Context pendant un draft

Le draft doit rester lié à son Actor Context d’origine.

Interdit :

```text
draft personnel
→ switch Mulykap
→ exécution silencieuse au nom de Mulykap
```

Le produit doit soit :

- conserver le draft dans son contexte initial ;
- demander explicitement de transférer/reformuler ;
- créer un nouveau draft.

---

# 103. Isolation multi-compte

Les drafts d’un Profile ne doivent pas apparaître chez un autre Profile.

Les fichiers privés restent isolés.

---

# 104. Pièce non synchronisée

Le cache ne doit jamais être l’unique copie d’une :

- photo capturée ;
- pièce jointe ;
- ressource locale unique ;
- draft significatif.

---

# 105. Privacy — contexte personnel

Le Mark personnel peut utiliser seulement les données personnelles nécessaires à l’intention.

Une demande de recherche externe ne doit pas envoyer tout le Profile à un moteur externe.

---

# 106. Privacy — contexte Space

Le Mark Space peut utiliser les données du Space autorisées pour la conséquence.

Il ne reçoit pas automatiquement tout le capital privé de la personne.

---

# 107. Frontière Profile ↔ Space

Invariant :

```text
composition
≠ transfert de données privées
```

Exemple :

```text
« Utilise mon passeport pour cette démarche du Space »
```

peut exiger une action explicite de partage/réutilisation.

Le simple fait d’agir pour un Space n’expose pas les ressources personnelles.

---

# 108. Confirmation de partage

Partager une ressource personnelle vers un contexte collectif peut demander confirmation selon sensibilité et owner.

Le Mark doit expliquer :

- quoi ;
- avec qui ;
- pour quelle finalité.

---

# 109. Feedback

Le feedback exprime le niveau réellement atteint.

Exemples :

```text
Brouillon enregistré sur cet appareil.
Document préparé.
Demande envoyée.
En attente de confirmation.
Réservation confirmée.
```

Jamais :

```text
Confirmé
```

si seul l’envoi a eu lieu.

---

# 110. État initial

```text
INITIAL
```

n’est pas Empty.

La surface est prête à recevoir.

---

# 111. États UX de référence

```text
INITIAL
DRAFT
UNDERSTANDING
NEEDS_CLARIFICATION
RESOLVED
NEEDS_CONFIRMATION

```

---

# 112. UNDERSTANDING

Le feedback peut être discret.

Pas d’animation spectaculaire d’IA.

Le système doit éviter une attente artificielle.

---

# 113. NEEDS_CLARIFICATION

Affiche :

```text
ce qui manque
+
une question
+
options éventuelles
```

Conserve l’input et les pièces.

---

# 114. RESOLVED

Le Mark a compris la destination ou la réalité.

Il peut :

- handoff immédiatement ;
- montrer une conséquence ;
- demander confirmation.

---

# 115. NEEDS_CONFIRMATION

Le focus devient la conséquence humaine.

L’input original reste accessible mais secondaire.

---

# 116. EXECUTING

Le Mark doit distinguer :

```text
préparation
envoi
attente
confirmation
```

si l’owner le nécessite.

---

# 117. COMPLETED

L’état terminé doit conduire naturellement vers :

- owner ;
- Maintenant ;
- En cours ;
- Moi ;
- Métier ;
- Nous ;
- ou fermeture.

Il ne cherche pas à continuer la conversation artificiellement.

---

# 118. UNKNOWN

Dire honnêtement :

```text
Makolo n’a pas assez d’éléments
```

ou :

```text
Makolo ne retrouve pas cette réalité dans ce contexte
```

sans inventer.

---

# 119. ERROR

Une erreur répond :

1. qu’est-ce qui a échoué ?
2. qu’est-ce qui a été conservé ?
3. que peut-on faire maintenant ?

---

# 120. Permission denied

Le Mark explique la limite.

Il ne révèle pas les données protégées qu’il n’a pas le droit d’afficher.

# 175. Formulation finale

> **Makolo Mark est l’action centrale unique par laquelle une personne donne naturellement à Makolo une intention, une question, une information, un texte, une voix, une photo, un document, un lien ou une situation, sans devoir connaître la taxonomie interne du produit. Il possède une seule identité visuelle et comportementale, identique dans le contexte personnel et dans un Space ; ce sont l’Actor Context, l’autorité, les owners et les conséquences légitimes qui changent. Le Mark comprend suffisamment, retrouve, réutilise, conserve, fait avancer, fait exister ou délègue lorsque les domaines propriétaires le permettent, mais il ne devient propriétaire d’aucune vérité, ne crée aucune Permission, ne transforme aucun support en fait canonique et ne publie rien implicitement. Il clarifie uniquement ce qui bloque réellement, demande confirmation lorsqu’une conséquence humaine le justifie, préserve les brouillons et pièces significatives en local-first sans faux succès, puis handoff vers la surface ou le domaine naturel. Personnel tend davantage vers trouver, obtenir, retrouver et poursuivre ; Space tend davantage vers créer, préparer, opérer et délivrer, mais cette différence est une tendance de conséquence, jamais deux Mark ni deux applications.**
